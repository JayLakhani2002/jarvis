# Decision Log

Why Jarvis is built the way it is. Each entry: the call, the reason, what was rejected. New significant decisions get appended here — this file is the memory a fresh session can't get from code alone.

## 2026-07-07 — v1 architecture

**Full 13-role org, not a lean 6-agent team.** Jay's explicit call, overriding Claude's lean recommendation. Mitigation: idle roles cost nothing until summoned; only the night shift consumes tokens on schedule.

**Draft-and-ratify, never auto-decide.** Agents prepare decisions (Recommendation/Why/Cost/Deadline) into the Decision Inbox; Jay ticks Approve. Rejected: "auto-decide small, escalate big" — blast radius and trust weren't worth the minutes saved. Unattended agents may write ONLY inside the vault: no sends, no commits/pushes, no deploys, no spend, no deletion of Jay's notes.

**Local Mac (launchd) runtime, not cloud routines.** Cloud agents can't touch the local vault — the whole system's ground truth. Cost: Mac must be awake at 02:00 (`sudo pmset repeat wakeorpoweron MTWRFSU 01:55:00`, still pending Jay). Cloud stays an option as Mac-off backup later.

**"24/7" = scheduled bursts, not a continuous loop.** A literal loop burns Max-plan limits idling and drifts unsupervised. Shifts: 02:00 work, 06:55 watchdog, 07:00 push, hourly snapshots, 21:00 sync — plus the always-on Telegram bot for on-demand.

**Night shift caps at ≤3 backlog items, one-track order.** Thesis → BSS (Sept 13) → Agora beta → funding → growth. Off-track items get skipped with a reason. Empty backlog → 3-line briefing, stop. Token discipline is a feature, not a limitation.

**Telegram over iMessage for push (pivot).** iMessage-to-self sent without error but never surfaced on Jay's phone (handle/sync ambiguity — unresolved, not worth debugging). Telegram bot (@Jarvis_for_Jay_bot) proved delivery instantly AND doubles as the two-way pocket interface. iMessage remains a silent fallback in `briefing_push.sh`.

**Bot answers ONLY Jay's chat_id.** The bot is publicly findable; any other chat is logged and ignored. The bot never initiates external contact — it replies to Jay and writes to the vault.

**Vault snapshots are local-only by design.** `~/.jarvis-vault-backup.git` (bare, outside iCloud) — because journals/health/faith content must never leave the machine. Only the 7 curated files (CLAUDE, GOALS, operating-core, Toolbox, Company OS, Briefing, Decision Inbox) sync to GitHub → claude.ai. Rejected: pushing full vault to a private GitHub repo — private ≠ on-machine.

**Excludes live in `$GIT_DIR/info/exclude`, not pathspecs.** Git's `:!**` pathspec glob silently failed to exclude nested dirs; repo-level ignore patterns match at any depth reliably. Also: iCloud can evict files (dataless) and crash `git add` — snapshot script triggers `brctl download` and retries next hour instead of failing loudly at 3am.

**Vault lives in Obsidian's own iCloud container.** `iCloud~md~obsidian/Documents/` — the only location iOS Obsidian auto-detects. `~/Documents/J's AI Brain` is a symlink into it so every script/agent path keeps working. History: the vault spent a day duplicated (local + generic iCloud Drive) and diverged; the symlink pattern ended that class of bug.

**One project home: `~/Documents/Jarvis`.** All scripts/plists/configs consolidated from 4 hidden dirs; plist sources are versioned, `install.sh` deploys them. Rule: never edit `~/Library/LaunchAgents` directly. Secrets in `config/` (gitignored); repo pushed private (github.com/JayLakhani2002/jarvis) with token verified absent.

**Jarvis features never outrank the one track.** Tool-collecting is Jay's documented procrastination pattern (vault CLAUDE.md). Tier-2 features wait until thesis runs ≥20h/wk sustained. Any feature request mid-crunch gets the trade-off flagged once, then Jay decides.

## 2026-07-09 — v1.4.1, full test pass + infra hardening

**Context7 checked before touching anything.** Verified `telegram_jarvis.py`'s `getUpdates`/`sendMessage` usage against current Telegram Bot API docs (offset recalculation, POST format) and `vault_rag.py`'s `/api/embed` usage against current Ollama API docs (request/response shape). Both matched exactly — no code changes needed. Recorded so the next session doesn't re-derive this: the bugs found below are all infra/environment issues, not API drift.

**launchd-spawned `/bin/bash` cannot read `.sh` files under `~/Documents/*` — silently, with no error the user can act on.** Discovered because `watchdog`'s real accumulated logs showed repeated "Operation not permitted," and forcing every suspect job via `launchctl start` proved it live: `dailysync` and `vaultsnapshot` had been failing for 46+ hours, undetected specifically because `watchdog` — the monitor — hit the identical bug and couldn't report on itself. Root cause: Documents/Desktop/Downloads are TCC-protected; a headless launchd process can't be shown the consent prompt, so first access just fails. The earlier v1.2 python fix (`/opt/homebrew/bin/python3` instead of Xcode's shimmed python) worked for a *different* reason than assumed at the time — bash was never the one opening those `.py` files, it only `exec`'d into python with the path as an argv, and homebrew python already has the access. Confirmed by direct test: wrapping a bash *script* the same way (`bash -c "exec ... watchdog.sh"`) did **not** fix it, because bash still has to `open()` the script to interpret its shebang. Real fix: `bin/run_sh.py` — python reads the script's source (proven working) and hands it to bash as an in-memory `-c` string, so bash never opens a Documents-folder path at all. Applied to all 5 plain-bash jobs (`watchdog`, `briefingpush`, `dailysync`, `vaultsnapshot`, `weeklysync`) and the paused `nightshift`. Verified on `watchdog` via forced `launchctl start`: TCC error gone, exit 0.

**`vault_snapshot.sh`'s `git add -A` can hang for minutes, not just fail.** iCloud holds infrequently-touched files "dataless" (evicted to save disk); first touch materializes them at ~2–10s each (measured directly on `00 Notes/Books/*`), so a full vault walk can legitimately take minutes — a real `git add` run hit my own 2-minute test timeout. The original script only handled a fast *failure* (`brctl download` + retry next hour); a *hang* left an orphaned `index.lock` that would silently no-op every future hourly run forever (git refuses to run with a stale lock present). Rewrote: bounded 240s timeout via background-PID + poll loop (macOS has no GNU `timeout`), lock removed defensively at both script start and on timeout, `brctl download` kicked off non-blocking to pre-warm the next run. Verified end-to-end: ran the fixed script, it materialized outstanding files and produced a real commit (4 files, including 2 days of accumulated Market Radar/Briefing/Backlog changes).

**Vault reads can hit a transient `OSError: [Errno 11] Resource deadlock avoided`.** Obsidian has the vault open live; iCloud file coordination briefly locks a note while Obsidian autosaves/syncs it. Was surfacing as wrong, not just failed: `voice_server.py`'s `/brief` caught the bare `OSError` and returned 404 "no briefing yet" — actively misleading, since the file exists and Siri would speak that lie aloud — and `dashboard.py`'s `health_series()` let it crash the whole render. Fixed both with retry-with-backoff readers (`read_resilient()` / `read_lines_resilient()`, ~8s ceiling) that distinguish `FileNotFoundError` (real 404) from a transient lock (retry, then honest 503 "temporarily locked" if it still hasn't cleared — never a false 404). Measured real contention: 0/8 failures in a clean sample; the one failure seen during testing was self-inflicted by stacking snapshot+dashboard+radar writes simultaneously, worse than any real usage pattern.

**`watchdog` must prune its own prior section, not just append.** The Morning Briefing is documented as "rewritten nightly by the 02:00 shift" — but night shift is paused (Jay's call), so nothing was resetting it, and watchdog had silently appended 7 duplicate sections into Jay's real briefing over one evening of testing. Now regexes out any previous `## 🩺 Watchdog (...)` block before appending the fresh one, so exactly one section exists regardless of night-shift cadence. Verified by running it twice back-to-back: section count stayed at 1. The 7 test-accumulated sections in the live file were manually cleaned up before this fix shipped.

**`dashboard.py`'s Decision Inbox tile was counting the entry-format template, not real decisions.** `count_boxes()` had a `section` parameter for exactly this but the Decision Inbox call site never passed it, so the `- [ ] Approve` line inside the vault's own "how to file a decision" example counted as a pending item. Caught by cross-checking the dashboard's "1 pending" against `vault_rag.py ask`'s independently-grounded "0 pending" and finding they disagreed — trust the vault file, not the tile. Fixed: scoped to `## Pending` only.

**Backlog.md had drifted from reality.** Four shipped features (market radar, weekly review draft, vault RAG, voice round-trip, dashboard) were never moved to Done despite running in production for up to two days; the market-radar item was still listed under "Now" describing the original firecrawl/Apify spec even though it shipped with a deliberate, already-documented deviation to arbeitnow.com. Backlog now matches what's actually deployed.

**Testing method: stub the network boundary, exercise real logic.** `telegram_jarvis.py`'s handlers were tested by importing the module and monkeypatching `send()` to capture output instead of hitting Telegram's API — this exercises the real `/status`, `/brief`, `/task` (real file write, self-cleaned after) and `/search` (real subprocess call to `vault_rag.py`) code paths without putting an unsolicited message on Jay's phone. `dailysync` (GitHub push) and `briefingpush` (Telegram send) were deployed with the fix but deliberately not force-run out-of-schedule, since that would push/send without Jay asking in the moment — they self-verify on their normal 21:00/07:00 slots and watchdog reports the result.

## 2026-07-11 — v1.5, logs out of ~/Documents + watchdog reality checks

**All logs moved to `~/Library/Logs/Jarvis/` — the EX_CONFIG poisoning class killed at the root.** On the Jul 9 reboot all 10 launchd jobs crash-looped with `EX_CONFIG` (exit 78) for ~2 days. Cause: launchd's `posix_spawn` opens a job's `StandardOut/ErrPath` *before* exec; the pre-existing log files lived under `~/Documents/Jarvis/logs`, which is both TCC-protected and iCloud-synced and carried a stale `com.apple.macl` xattr — so the open was denied and the job never started. Fresh files worked, which is exactly why it read as intermittent rather than total. Fix: every plist (10 active + the paused nightshift) and every app-level log path (`telegram_jarvis.py` LOG, `night_shift.sh`, `weekly_brain_sync.sh`, and watchdog's `night_shift.log` reads) now write to `~/Library/Logs/Jarvis/` — outside both TCC and iCloud. `install.sh` `mkdir -p`s it before bootstrapping (single owner of dir creation; scripts just append). Old logs stay archived in `~/Documents/Jarvis/logs` (gitignored). Rejected: scrubbing the `com.apple.macl` xattr / chmod-ing the Documents files on boot — fragile and races iCloud; moving out of the protected tree removes the failure mode entirely instead of papering over it. Non-log paths (vault, config) deliberately stay under `~/Documents` — they're read by TCC-approved homebrew python, not opened by launchd pre-exec.

**Watchdog now checks liveness, not just labels — and alerts over a channel that survives the outage.** The old watchdog only verified each label appeared in `launchctl list`; a crash-looping job still shows its label (PID `-`, last exit 78), so it reported "all healthy" straight through a 2-day outage — the same blind spot that hid the v1.4.1 bash-TCC outage. It now parses the PID / exit-status columns: daemons (`telegrambot`, `voiceserver`) with PID `-`, and *any* job with exit 78, are ⛔ CRITICAL; other persistent non-zero exits are ⚠️; signal deaths (negative, e.g. -15 SIGTERM on reload) are ignored as normal. NEW: whenever any ⛔ exists, watchdog pushes it straight to Telegram via the Bot API (`TOKEN`/`CHAT_ID` parsed from `config/telegram.conf`, never printed; skipped silently if absent), independent of the `briefingpush` job. Rationale: both prior multi-day outages were invisible precisely because the alert path (the Morning Briefing, delivered by *another* launchd job) was itself down — a direct push from the watchdog is the only channel that survives when the jobs are broken, and `sendMessage` works even if the `telegrambot` polling daemon is dead. `telegrambot` was also added to the watched-job list (the old loop omitted it).

## 2026-07-11 — v1.6, email triage

**IMAP + Gmail app password, not the Gmail API or Apple Mail.** The job needs to read one inbox unattended with zero new dependencies and no secret beyond what the existing config pattern already handles. IMAP over `imaplib` is pure stdlib (imaplib/email/ssl) — no OAuth dance, no `google-api-python-client`, no token-refresh daemon — and a Gmail app password is a single `KEY=VALUE` string that drops straight into a gitignored `config/email.conf`, exactly mirroring how `telegram.conf` holds the bot token. Rejected: the **Gmail API** (OAuth client setup, a refresh token to store and rotate, a pip dependency tree — all overkill for read-only triage) and scripting **Apple Mail** (AppleScript/SQLite against the local Mail store is brittle across macOS versions and pulls the same TCC-under-launchd problems we just spent v1.4.1/v1.5 eliminating). Trade-off accepted: app passwords require 2-Step Verification on the account and are a long-lived credential — mitigated by keeping it in the gitignored config only, never logging or printing it (defensive scrub if it ever appears in an exception string), and the read-only IMAP surface below.

**Read-only is enforced at the protocol verb level, not just by intent.** The only IMAP verbs issued are LOGIN, SELECT with `readonly=True`, SEARCH, FETCH `(BODY.PEEK[])`, and LOGOUT. `readonly=True` opens the mailbox as EXAMINE (no state changes permitted server-side), and **BODY.PEEK** is the whole point — a plain `BODY[]` fetch sets the `\Seen` flag as a side effect, so PEEK is what guarantees reading Jay's mail never marks it read. No STORE, COPY, MOVE, or EXPUNGE exists anywhere in the code. This is the draft-only boundary expressed in IMAP: the job can *learn* from the inbox, never *change* it.

**Dormant (exit 0) vs configured-but-broken (exit 1) — the exit code carries intent to the watchdog.** With no `config/email.conf` (or an empty user/pass), the job logs one line and exits **0**: being unconfigured is a valid state by design (Jay hasn't done the 5-min setup yet), so the watchdog's non-zero-exit check must stay quiet — no daily false alarm. Auth/network/IMAP failures exit **1**, so the *same* watchdog check flags a real breakage. This split is why the job doesn't just skip silently on error: a configured inbox that stops fetching is a problem Jay should see, an unconfigured one is not. Claude-side degradation (JSON parse failure, triage timeout) is deliberately *not* a failure — it still writes a count-only briefing section and exits 0, because a degraded briefing beats a dead one and the mail was still read fine.

**Drafts are drafted, never sent — same ratify boundary as every other agent output.** Reply drafts land as a `## Re: …` block per message in `06 Company/Drafts/Email Replies — <date>.md`, each ending `- [ ] Approve — then Jay sends it himself from Gmail`. There is no SMTP anywhere; Jarvis has no send path at all. The briefing gets a self-pruning `## 📧 Inbox (<date>)` section built with the exact regex-prune-then-append pattern `watchdog.sh` uses (Morning Briefing is meant to be reset nightly by the 02:00 shift, which is paused — so each writer prunes its own prior section to avoid unbounded growth). Same-day drafts file is overwritten so reruns are idempotent. Resilient vault I/O helpers (`read_resilient`/`write_resilient`, retry on EDEADLK) were copied from `telegram_jarvis.py` rather than imported, so the job has no cross-script dependency.
