# Decision Log

Why Jarvis is built the way it is. Each entry: the call, the reason, what was rejected. New significant decisions get appended here — this file is the memory a fresh session can't get from code alone.

## 2026-07-07 — v1 architecture

**Full 13-role org, not a lean 6-agent team.** The operator's explicit call, overriding Claude's lean recommendation. Mitigation: idle roles cost nothing until summoned; only the night shift consumes tokens on schedule.

**Draft-and-ratify, never auto-decide.** Agents prepare decisions (Recommendation/Why/Cost/Deadline) into the Decision Inbox; the operator ticks Approve. Rejected: "auto-decide small, escalate big" — blast radius and trust weren't worth the minutes saved. Unattended agents may write ONLY inside the vault: no sends, no commits/pushes, no deploys, no spend, no deletion of the operator's notes.

**Local Mac (launchd) runtime, not cloud routines.** Cloud agents can't touch the local vault — the whole system's ground truth. Cost: Mac must be awake at 02:00 (`sudo pmset repeat wakeorpoweron MTWRFSU 01:55:00`, still pending the operator). Cloud stays an option as Mac-off backup later.

**"24/7" = scheduled bursts, not a continuous loop.** A literal loop burns Max-plan limits idling and drifts unsupervised. Shifts: 02:00 work, 06:55 watchdog, 07:00 push, hourly snapshots, 21:00 sync — plus the always-on Telegram bot for on-demand.

**Night shift caps at ≤3 backlog items, one-track order.** The one-track priority order (deadline-ranked workstreams). Off-track items get skipped with a reason. Empty backlog → 3-line briefing, stop. Token discipline is a feature, not a limitation.

**Telegram over iMessage for push (pivot).** iMessage-to-self sent without error but never surfaced on the operator's phone (handle/sync ambiguity — unresolved, not worth debugging). Telegram bot (@your_bot_name) proved delivery instantly AND doubles as the two-way pocket interface. iMessage remains a silent fallback in `briefing_push.sh`.

**Bot answers ONLY the operator's chat_id.** The bot is publicly findable; any other chat is logged and ignored. The bot never initiates external contact — it replies to the operator and writes to the vault.

**Vault snapshots are local-only by design.** `~/.jarvis-vault-backup.git` (bare, outside iCloud) — because sensitive personal notes (journals, health logs) must never leave the machine. Only the 7 curated files (CLAUDE, GOALS, operating-core, Toolbox, Company OS, Briefing, Decision Inbox) sync to GitHub → claude.ai. Rejected: pushing full vault to a private GitHub repo — private ≠ on-machine.

**Excludes live in `$GIT_DIR/info/exclude`, not pathspecs.** Git's `:!**` pathspec glob silently failed to exclude nested dirs; repo-level ignore patterns match at any depth reliably. Also: iCloud can evict files (dataless) and crash `git add` — snapshot script triggers `brctl download` and retries next hour instead of failing loudly at 3am.

**Vault lives in Obsidian's own iCloud container.** `iCloud~md~obsidian/Documents/` — the only location iOS Obsidian auto-detects. `~/Documents/J's AI Brain` is a symlink into it so every script/agent path keeps working. History: the vault spent a day duplicated (local + generic iCloud Drive) and diverged; the symlink pattern ended that class of bug.

**One project home: `~/Documents/Jarvis`.** All scripts/plists/configs consolidated from 4 hidden dirs; plist sources are versioned, `install.sh` deploys them. Rule: never edit `~/Library/LaunchAgents` directly. Secrets in `config/` (gitignored); repo pushed private (github.com/JayLakhani2002/jarvis) with token verified absent.

**Jarvis features never outrank the one track.** Tier-2 features wait until Track A runs ≥20h/wk sustained. Any feature request mid-crunch gets the trade-off flagged once, then the operator decides.

## 2026-07-09 — v1.4.1, full test pass + infra hardening

**Context7 checked before touching anything.** Verified `telegram_jarvis.py`'s `getUpdates`/`sendMessage` usage against current Telegram Bot API docs (offset recalculation, POST format) and `vault_rag.py`'s `/api/embed` usage against current Ollama API docs (request/response shape). Both matched exactly — no code changes needed. Recorded so the next session doesn't re-derive this: the bugs found below are all infra/environment issues, not API drift.

**launchd-spawned `/bin/bash` cannot read `.sh` files under `~/Documents/*` — silently, with no error the user can act on.** Discovered because `watchdog`'s real accumulated logs showed repeated "Operation not permitted," and forcing every suspect job via `launchctl start` proved it live: `dailysync` and `vaultsnapshot` had been failing for 46+ hours, undetected specifically because `watchdog` — the monitor — hit the identical bug and couldn't report on itself. Root cause: Documents/Desktop/Downloads are TCC-protected; a headless launchd process can't be shown the consent prompt, so first access just fails. The earlier v1.2 python fix (`/opt/homebrew/bin/python3` instead of Xcode's shimmed python) worked for a *different* reason than assumed at the time — bash was never the one opening those `.py` files, it only `exec`'d into python with the path as an argv, and homebrew python already has the access. Confirmed by direct test: wrapping a bash *script* the same way (`bash -c "exec ... watchdog.sh"`) did **not** fix it, because bash still has to `open()` the script to interpret its shebang. Real fix: `bin/run_sh.py` — python reads the script's source (proven working) and hands it to bash as an in-memory `-c` string, so bash never opens a Documents-folder path at all. Applied to all 5 plain-bash jobs (`watchdog`, `briefingpush`, `dailysync`, `vaultsnapshot`, `weeklysync`) and the paused `nightshift`. Verified on `watchdog` via forced `launchctl start`: TCC error gone, exit 0.

**`vault_snapshot.sh`'s `git add -A` can hang for minutes, not just fail.** iCloud holds infrequently-touched files "dataless" (evicted to save disk); first touch materializes them at ~2–10s each (measured directly on `00 Notes/Books/*`), so a full vault walk can legitimately take minutes — a real `git add` run hit my own 2-minute test timeout. The original script only handled a fast *failure* (`brctl download` + retry next hour); a *hang* left an orphaned `index.lock` that would silently no-op every future hourly run forever (git refuses to run with a stale lock present). Rewrote: bounded 240s timeout via background-PID + poll loop (macOS has no GNU `timeout`), lock removed defensively at both script start and on timeout, `brctl download` kicked off non-blocking to pre-warm the next run. Verified end-to-end: ran the fixed script, it materialized outstanding files and produced a real commit (4 files, including 2 days of accumulated Market Radar/Briefing/Backlog changes).

**Vault reads can hit a transient `OSError: [Errno 11] Resource deadlock avoided`.** Obsidian has the vault open live; iCloud file coordination briefly locks a note while Obsidian autosaves/syncs it. Was surfacing as wrong, not just failed: `voice_server.py`'s `/brief` caught the bare `OSError` and returned 404 "no briefing yet" — actively misleading, since the file exists and Siri would speak that lie aloud — and `dashboard.py`'s `health_series()` let it crash the whole render. Fixed both with retry-with-backoff readers (`read_resilient()` / `read_lines_resilient()`, ~8s ceiling) that distinguish `FileNotFoundError` (real 404) from a transient lock (retry, then honest 503 "temporarily locked" if it still hasn't cleared — never a false 404). Measured real contention: 0/8 failures in a clean sample; the one failure seen during testing was self-inflicted by stacking snapshot+dashboard+radar writes simultaneously, worse than any real usage pattern.

**`watchdog` must prune its own prior section, not just append.** The Morning Briefing is documented as "rewritten nightly by the 02:00 shift" — but night shift is paused (the operator's call), so nothing was resetting it, and watchdog had silently appended 7 duplicate sections into the operator's real briefing over one evening of testing. Now regexes out any previous `## 🩺 Watchdog (...)` block before appending the fresh one, so exactly one section exists regardless of night-shift cadence. Verified by running it twice back-to-back: section count stayed at 1. The 7 test-accumulated sections in the live file were manually cleaned up before this fix shipped.

**`dashboard.py`'s Decision Inbox tile was counting the entry-format template, not real decisions.** `count_boxes()` had a `section` parameter for exactly this but the Decision Inbox call site never passed it, so the `- [ ] Approve` line inside the vault's own "how to file a decision" example counted as a pending item. Caught by cross-checking the dashboard's "1 pending" against `vault_rag.py ask`'s independently-grounded "0 pending" and finding they disagreed — trust the vault file, not the tile. Fixed: scoped to `## Pending` only.

**Backlog.md had drifted from reality.** Four shipped features (market radar, weekly review draft, vault RAG, voice round-trip, dashboard) were never moved to Done despite running in production for up to two days; the market-radar item was still listed under "Now" describing the original firecrawl/Apify spec even though it shipped with a deliberate, already-documented deviation to arbeitnow.com. Backlog now matches what's actually deployed.

**Testing method: stub the network boundary, exercise real logic.** `telegram_jarvis.py`'s handlers were tested by importing the module and monkeypatching `send()` to capture output instead of hitting Telegram's API — this exercises the real `/status`, `/brief`, `/task` (real file write, self-cleaned after) and `/search` (real subprocess call to `vault_rag.py`) code paths without putting an unsolicited message on the operator's phone. `dailysync` (GitHub push) and `briefingpush` (Telegram send) were deployed with the fix but deliberately not force-run out-of-schedule, since that would push/send without the operator asking in the moment — they self-verify on their normal 21:00/07:00 slots and watchdog reports the result.

## 2026-07-11 — v1.5, logs out of ~/Documents + watchdog reality checks

**All logs moved to `~/Library/Logs/Jarvis/` — the EX_CONFIG poisoning class killed at the root.** On the Jul 9 reboot all 10 launchd jobs crash-looped with `EX_CONFIG` (exit 78) for ~2 days. Cause: launchd's `posix_spawn` opens a job's `StandardOut/ErrPath` *before* exec; the pre-existing log files lived under `~/Documents/Jarvis/logs`, which is both TCC-protected and iCloud-synced and carried a stale `com.apple.macl` xattr — so the open was denied and the job never started. Fresh files worked, which is exactly why it read as intermittent rather than total. Fix: every plist (10 active + the paused nightshift) and every app-level log path (`telegram_jarvis.py` LOG, `night_shift.sh`, `weekly_brain_sync.sh`, and watchdog's `night_shift.log` reads) now write to `~/Library/Logs/Jarvis/` — outside both TCC and iCloud. `install.sh` `mkdir -p`s it before bootstrapping (single owner of dir creation; scripts just append). Old logs stay archived in `~/Documents/Jarvis/logs` (gitignored). Rejected: scrubbing the `com.apple.macl` xattr / chmod-ing the Documents files on boot — fragile and races iCloud; moving out of the protected tree removes the failure mode entirely instead of papering over it. Non-log paths (vault, config) deliberately stay under `~/Documents` — they're read by TCC-approved homebrew python, not opened by launchd pre-exec.

**Watchdog now checks liveness, not just labels — and alerts over a channel that survives the outage.** The old watchdog only verified each label appeared in `launchctl list`; a crash-looping job still shows its label (PID `-`, last exit 78), so it reported "all healthy" straight through a 2-day outage — the same blind spot that hid the v1.4.1 bash-TCC outage. It now parses the PID / exit-status columns: daemons (`telegrambot`, `voiceserver`) with PID `-`, and *any* job with exit 78, are ⛔ CRITICAL; other persistent non-zero exits are ⚠️; signal deaths (negative, e.g. -15 SIGTERM on reload) are ignored as normal. NEW: whenever any ⛔ exists, watchdog pushes it straight to Telegram via the Bot API (`TOKEN`/`CHAT_ID` parsed from `config/telegram.conf`, never printed; skipped silently if absent), independent of the `briefingpush` job. Rationale: both prior multi-day outages were invisible precisely because the alert path (the Morning Briefing, delivered by *another* launchd job) was itself down — a direct push from the watchdog is the only channel that survives when the jobs are broken, and `sendMessage` works even if the `telegrambot` polling daemon is dead. `telegrambot` was also added to the watched-job list (the old loop omitted it).

## 2026-07-11 — v1.6, email triage

**IMAP + Gmail app password, not the Gmail API or Apple Mail.** The job needs to read one inbox unattended with zero new dependencies and no secret beyond what the existing config pattern already handles. IMAP over `imaplib` is pure stdlib (imaplib/email/ssl) — no OAuth dance, no `google-api-python-client`, no token-refresh daemon — and a Gmail app password is a single `KEY=VALUE` string that drops straight into a gitignored `config/email.conf`, exactly mirroring how `telegram.conf` holds the bot token. Rejected: the **Gmail API** (OAuth client setup, a refresh token to store and rotate, a pip dependency tree — all overkill for read-only triage) and scripting **Apple Mail** (AppleScript/SQLite against the local Mail store is brittle across macOS versions and pulls the same TCC-under-launchd problems we just spent v1.4.1/v1.5 eliminating). Trade-off accepted: app passwords require 2-Step Verification on the account and are a long-lived credential — mitigated by keeping it in the gitignored config only, never logging or printing it (defensive scrub if it ever appears in an exception string), and the read-only IMAP surface below.

**Read-only is enforced at the protocol verb level, not just by intent.** The only IMAP verbs issued are LOGIN, SELECT with `readonly=True`, SEARCH, FETCH `(BODY.PEEK[])`, and LOGOUT. `readonly=True` opens the mailbox as EXAMINE (no state changes permitted server-side), and **BODY.PEEK** is the whole point — a plain `BODY[]` fetch sets the `\Seen` flag as a side effect, so PEEK is what guarantees reading the operator's mail never marks it read. No STORE, COPY, MOVE, or EXPUNGE exists anywhere in the code. This is the draft-only boundary expressed in IMAP: the job can *learn* from the inbox, never *change* it.

**Dormant (exit 0) vs configured-but-broken (exit 1) — the exit code carries intent to the watchdog.** With no `config/email.conf` (or an empty user/pass), the job logs one line and exits **0**: being unconfigured is a valid state by design (the operator hasn't done the 5-min setup yet), so the watchdog's non-zero-exit check must stay quiet — no daily false alarm. Auth/network/IMAP failures exit **1**, so the *same* watchdog check flags a real breakage. This split is why the job doesn't just skip silently on error: a configured inbox that stops fetching is a problem the operator should see, an unconfigured one is not. Claude-side degradation (JSON parse failure, triage timeout) is deliberately *not* a failure — it still writes a count-only briefing section and exits 0, because a degraded briefing beats a dead one and the mail was still read fine.

**Drafts are drafted, never sent — same ratify boundary as every other agent output.** Reply drafts land as a `## Re: …` block per message in `06 Company/Drafts/Email Replies — <date>.md`, each ending `- [ ] Approve — then the operator sends it himself from Gmail`. There is no SMTP anywhere; Jarvis has no send path at all. The briefing gets a self-pruning `## 📧 Inbox (<date>)` section built with the exact regex-prune-then-append pattern `watchdog.sh` uses (Morning Briefing is meant to be reset nightly by the 02:00 shift, which is paused — so each writer prunes its own prior section to avoid unbounded growth). Same-day drafts file is overwritten so reruns are idempotent. Resilient vault I/O helpers (`read_resilient`/`write_resilient`, retry on EDEADLK) were copied from `telegram_jarvis.py` rather than imported, so the job has no cross-script dependency.

## 2026-07-11 — v1.7, CFO net-worth tracker

**A generic column-mapper (`config/banks.json`), not per-bank hardcoded parsers — the operator's explicit call.** Each bank gets one JSON entry: a filename `match` substring, the display `account`, delimiter/encoding, `date_col`+`date_fmt`, and either an `amount_col` or a `balance_col`. Adding a bank is a config edit the operator does himself (the setup recipe is in vault Drafts), never a code change — so the job needs no new deps and no dev round-trip per bank. Rejected: hardcoding N26/Revolut/etc. parsers in Python (brittle, and every new bank or a bank changing its export format would mean editing and re-testing code). Trade-off accepted: a malformed mapping surfaces as a file in `finance/failed/` rather than a friendly error, which the setup recipe's troubleshooting section covers.

**Two balance modes, because bank exports split into two shapes.** *Balance mode* (`balance_col` set): the account balance is the balance value of the **newest-dated row** — for exports that carry a running balance. *Sum mode* (`balance_col` null): balance = `starting_balance` + Σ of every `amount_col` — for transaction-only exports with no balance column, where the operator seeds the pre-export balance once. One mapper covers both; the mode is implied by whether `balance_col` is present.

**Decimal convention is per-bank config, not guessed.** `decimal: ","` = German (`1.234,56` → strip thousands dots, comma→dot); `decimal: "."` = US (`1,234.56` → strip thousands commas). Currency symbols (`€`/`EUR`/`$`/`£`), NBSP, and whitespace are stripped before parsing. Guessing the convention from the data is ambiguous (`1.234` is 1234 in Germany, 1.234 in the US), so it's declared. A UTF-8 BOM is tolerated (`utf-8-sig` when encoding is utf-8) and headers are stripped/de-BOM'd, since real bank CSVs ship both.

**GOALS.md gets a marker-managed block, and nothing is written until the first successful ingest.** The job maintains exactly the region between `<!-- jarvis:networth:start -->` and `<!-- jarvis:networth:end -->`, replacing it by string-slice so every byte outside the markers is preserved verbatim (the operator's hand-written GOALS content is never at risk); if the markers are absent it appends the block once with one blank line before. Critically, GOALS is only touched when state holds ≥1 account — a run that ingests nothing (dormant) or only fails leaves GOALS completely alone, so an empty/broken run can never blank out the block. Numbers are English-formatted (`€12,345.67`), not German, because the vault is English. This mirrors the self-pruning-section discipline from watchdog/email-triage but is stricter: a single fixed region, not a prune-and-append.

**`finance/` is gitignored — bank data must never be committable.** The watched folders (`inbox/`/`processed/`/`failed/`) and `state.json` (which holds real balances) live under `~/Documents/Jarvis/finance/`, added to `.gitignore` alongside `config/` and `dashboard/`. Same never-leaves-the-machine rule as vault snapshots and the RAG index: transaction CSVs and balances stay local. Logs get counts and derived balances only — never a row's contents.

**Dormant (exit 0) vs broken (exit 1), reusing the v1.6 exit-code split.** Empty inbox → one dormant log line, exit 0 (watchdog stays quiet — the operator hasn't dropped a file yet, a valid idle state). `banks.json` missing/invalid **while files are waiting** → exit 1 and the files are left in the inbox untouched (so the next run ingests them once the config is fixed, rather than quarantining good data over a config typo). Any file that moves to `failed/` (no mapping match, zero parseable rows, decode/csv error) also forces exit 1, but never stops the other files in the batch from processing. Same principle as email triage: the exit code carries intent to the watchdog, so an unconfigured job is silent and a real breakage is loud.

## 2026-07-11 — v1.8, briefing content spec (deterministic commander brief)

**Deterministic assembler, not a claude-composed message.** The operator's ratified 07:00 brief is built by `bin/briefing_build.py` (stdlib only, NO `claude -p` anywhere) by reading numbers straight from vault files. Rejected: having the night shift (or a headless claude call) write the terse message. Reasons: (1) every number is copied from a source, so nothing is hallucinated — a claude-composed brief could invent a habit streak or a deadline count; (2) it's unit-testable with synthetic fixtures (a prompt isn't); (3) it's free and instant, and it runs correctly even while the night shift is paused, since it reads the sections other jobs already maintain. The night shift's role was reshaped (`night_shift_prompt.md`) to *enrich the note's body sections* (Decision Inbox reasoning, backlog context) rather than hand-format the push — so the unpaused shift feeds the builder instead of fighting it.

**Deadline-weighted top-3, not backlog order.** The three "today" items come from the Backlog `## Now (one-track)` unchecked items, but ranked by urgency: each item is keyword-matched to a track (per-track keyword sets, case-insensitive), matched items sort by their track's deadline nearest-first (stable, so ties keep backlog order), unmatched items follow in backlog order. Consequence worth noting: a nearer-deadline workstream outranks a farther one in the brief, even though the night-shift *work* order follows strategic priority — the brief ranks by calendar pressure, the shift ranks by strategic priority; both are intentional. Deadline dates live in one place — `bin/deadlines.py` — imported by both `dashboard.py` (tiles) and `briefing_build.py` (countdown + weighting); when a date moves, one edit updates every consumer.

**Omit-over-placeholder.** Every source that is empty or unavailable drops its whole line — no "N/A", no "0 pending", no empty calendar row. A commander brief with 8 real lines beats one padded to 15 with zeros. Zero-pending Decision Inbox, no health log yet, no email section, no daily-notes folder, no Calendar grant — each simply doesn't appear. Hard cap is 15 lines; if a fully-populated brief ever exceeds it, lines drop in a fixed order (todos → calendar → radar) so the load-bearing lines (deadlines, top-3, decisions, health) always survive.

**Builder-first with raw-note fallback in `briefing_push.sh`.** The push runs the builder and sends its stdout only if it exits 0 AND is non-empty; on any non-zero exit or empty output it falls back to the previous behavior (send the sed-cleaned raw note). So a bug in the builder degrades the 07:00 push to "the old briefing" instead of "no briefing" — the same degraded-beats-dead principle as email triage. The builder itself exits 0 with a best-effort partial brief even when several sources fail (each parser is exception-wrapped to omit just its line); it exits 1 only when the briefing note itself is unreadable/unwritable, which is exactly the case where the fallback should fire.

**Self-pruning brief block inserted under the H1, bounded by a planted `---`.** The brief is also written into the Morning Briefing note as a `## ⚡ 07:00 Brief (date)` section placed directly beneath the note's title (not appended at the end) so Telegram `/brief` — which sends the raw note — leads with it. The established watchdog/email "prune until the next `## `" idiom is unsafe here: inserted mid-note, "until next `##`" would swallow the note's own body. So the block is instead bounded by a `---` terminator planted as its last line, and pruned with a non-greedy regex from its header to that first `---`. Rejected: HTML-comment markers (networth style) — `/brief` sends the note verbatim, so `<!-- -->` markers would show as literal text on the operator's phone; the `---` renders as a clean horizontal rule instead. Insert is idempotent (prune-then-insert), verified to stay at one section across repeated runs with the title still first.

**Calendar is best-effort and honest about TCC.** The 📅 line shells `icalBuddy eventsToday` (10s timeout, `-nc` the only flag used), and omits the line + logs once on any failure or empty output. Headless launchd has no Calendar access until the operator runs `icalBuddy` once in Terminal to trigger the one-time TCC grant — documented in vault `06 Company/Drafts/Jarvis Briefing v1.8 — Notes.md`, alongside `brew install ical-buddy`. ## 2026-07-17 — v2 Phase 2: voice + motion/UI overhaul

**Deepgram and ElevenLabs both wired with ZERO new dependencies.** Electron 43 ships Node 24.18, which has a global `fetch` *and* a global `WebSocket` — so ElevenLabs TTS is one `fetch` (`POST /v1/text-to-speech/{voice_id}`, `xi-api-key` header, `eleven_multilingual_v2`) and Deepgram STT is one `new WebSocket`. The catch found via context7: Node's global WebSocket is the WHATWG/undici one, which **cannot set an `Authorization` header** (only the `ws` package can). Deepgram documents a purpose-built escape hatch — `Sec-WebSocket-Protocol: token, <key>`, i.e. `new WebSocket(url, ['token', key])` — intended for exactly this class of client. Rejected: adding the `ws` package, and adding either vendor SDK, for what is ~40 lines of stdlib.

**Mic audio flows renderer → main → Deepgram; the key never enters the renderer.** The obvious design (browser opens the Deepgram socket directly) would either expose the API key to the window or require a token-minting server. Instead the renderer captures mic audio and ships raw PCM over IPC; `main.js` relays it to Deepgram and sends transcripts back. Consequence: CSP stays at `connect-src 'none'` — the window makes no network calls at all. `voice:chunk` uses `ipcRenderer.send` (fire-and-forget), not `invoke`, because it fires many times a second and there is no reply worth awaiting. Capture is an **AudioWorklet** (`renderer/pcm-worklet.js`) doing float32→linear16 off the main thread; rejected `ScriptProcessorNode` (deprecated, runs on the main thread, glitches under load). **No resampling** — we send the AudioContext's native rate and tell Deepgram `sample_rate=<actual>`, deleting a whole class of resampler bugs.

**The TTS privacy gate is code, not a prompt (`app/voice.js` → `speakable()`).** PRD §10: voice out is a cloud path, so the never-leaves-the-machine rule (journals/health/faith) applies to the *speaker*, not just the disk. A turn is refused two ways: (1) **path tainting** — `main.js` records every `file_path`/`command` the turn's tools touched, and a hit on `01 Journals`/health/faith blocks speech (exact, not guesswork); (2) a **keyword backstop** for content recited from context rather than freshly read. A block is not an error: the reply still renders on screen with a quiet italic note. `ponytail:` comment names the ceiling — if the keyword net over-blocks, drop it and taint purely on tool reads. Self-checked in `voice.js`.

**Dormant until configured, per the v1.6/v1.7 exit-intent split.** No `config/voice-app.conf` → `loadConfig()` returns null, status strip reads `voice dormant`, mic button disabled with a tooltip, everything else works. Either key alone → `voice partial` (Deepgram-only = talk, read replies; ElevenLabs-only = type, hear replies). Setup recipe lives in vault `06 Company/Drafts/Jarvis Voice v2 — Setup.md`, matching how email triage and the CFO tracker document their own 5-minute setup.

**UI overhaul per the ui-ux-pro-max design system — with two of its recommendations deliberately overridden.** Adopted: Dark Mode (OLED) `#020617` base, minimal-glow (`text-shadow`) over brightness, `ease-out` for entering motion, 44×44 touch targets, `:focus-visible` rings, 68ch line length, `cursor-pointer` everywhere clickable. **Overridden (1):** the system recommends Fira Code/Fira Sans via Google Fonts — rejected, because the HUD decision (2026-07-08) already established that CDN fonts are out (must render offline) and the app's CSP blocks external origins; system `ui-monospace` stack instead. **Overridden (2):** its landing-page "Product Demo + Features" section pattern is for marketing sites, irrelevant to a personal command center — ignored. Palette deliberately matches `dashboard.py`'s cyan/amber HUD so both surfaces read as one system.

**Emoji were being used as icons — fixed.** The v2 Phase 1 shell shipped 📁/📄/⚒/⚠ as UI icons, which the design checklist flags outright. Replaced with an inline SVG sprite (Lucide geometry, 24-grid, `currentColor`, 1.75 stroke) defined once in `index.html` — no external icon dependency, no CDN, CSP-clean.

**Motion is constrained to one element, and fully removable.** The UX rules cap continuous animation at 1–2 elements per view, so the **orb is the only thing that loops**: three counter-rotating SVG rings plus a glow. Messages get a single 260ms `rise` on entry and never again. Critically, the orb is **audio-reactive off real mic data, not a fake loop** — the worklet ships the frame's peak amplitude alongside the PCM, and it drives a `--level` CSS custom property that scales the glow and the mic button's ring. A full `prefers-reduced-motion` block kills every animation and transition; state stays legible because the orb also carries a text label (`ready`/`listening`/`thinking`/`speaking`) and a color — never color alone, same rule the dashboard follows.

## 2026-09-03 — v1.10, RAG eval harness

**Retrieval and answer quality are measured separately, and reported separately.** `bin/rag_eval.py` scores `vault_rag.top_k()` against a 20-question golden set (`evals/goldens.json`, gitignored — the questions are vault-specific). A bad answer caused by bad retrieval is a different defect from a bad answer despite good retrieval, and collapsing them into one "quality" score destroys the only information that tells the operator which half to fix. First measured baseline: **MRR 0.40, hit@1 6/20, hit@3 9/20, hit@5 11/20** — nearly half the questions do not surface the correct note in the top 5. That number is the deliverable; improving it is a separate piece of work that now has a scoreboard.

**hit@k and MRR only — nDCG and MAP deliberately rejected.** At n=20 with 1–2 relevant notes per question and binary relevance, nDCG's log-discount curve and MAP's multi-relevant averaging are noise-dominated: they add implementation surface for a number that cannot distinguish two systems at this sample size. Both are worth adding if the golden set ever reaches the hundreds. Standard conventions kept intact: hit@k counts a question as a hit if **any** gold source appears in the top k, and MRR uses the rank of the **first** gold source and ignores the rest — that is MRR's textbook definition, not a shortcut. Rates are printed with their counts (`hit@5=11/20`, not `55%`) because a bare percentage implies precision that 20 samples do not support.

**Chunks are collapsed to files before ranking.** `top_k` returns chunks, and one note can own several of them; a note appearing three times is still one retrieved document. Ranking without collapsing would inflate every metric.

**The judge grades with a discrete verdict, reference-guided, reasoning first.** `correct/partial/incorrect` rather than a 1–5 Likert scale: a single-turn judge's noise lives precisely between adjacent Likert points, and at n=20 that noise swamps the signal. Coarser but reproducible run-to-run, which is the entire purpose of a trend line. The judge sees **both** the retrieved context and the gold sources, with a separate `faithful_to_context` flag, so one call distinguishes a retrieval failure from a generation failure. Output is constrained by `claude -p --output-format json --json-schema`, so the shape is validated server-side rather than scraped out of free text. Known limitation, reported rather than solved: a Claude judge grading Claude-generated answers carries self-preference bias; reference-guided grading is the available mitigation without a second model.

**A failed CLI call is a failed measurement, not a wrong answer.** A `claude -p` invocation can exit 0 and still print something that is not an answer — a hook refusal, an auth error. Found live: a hook-block string was being passed to the judge as though it were the system's answer, and billed $0.36 to grade garbage. `run_claude` now returns `None` on a non-zero exit, empty output, or a known failure marker; the row is recorded as `generation_error`, excluded from the aggregate, and never judged. Same rule for an unparseable judge, which retries once and is then excluded. Silently defaulting either case to a score would bias the weekly trend in the one direction nobody would notice.

**The scheduled run is `--retrieval-only`.** Sunday 19:00, after `weeklysync`. Retrieval scoring is free, deterministic, needs no network, and keeps vault content on the machine — the judge would send gold note text to the API on a recurring schedule, which the repo's own never-leaves-the-machine rule makes a decision rather than a default. The judge stays available on demand, and `--fail-under` exists for CI. Consistent with `emailtriage`: both the answerer and the judge run with `--tools '' --strict-mcp-config`, since neither needs a single tool.
